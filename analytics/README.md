# Analytics (Phase 7)

Written 2026-10-12. For the operator (English). **Nothing here holds a real number yet.** The real database folder is empty on purpose; the dashboard and report you can open today run on invented DEMO data and say so in a banner.

## 1. What this is

A small tracker, dashboard and weekly report that tell you, from numbers you copy out of each platform's own insights pages, whether each pilot persona should be **scaled, kept, fixed or retired** under `strategy/portfolio.md` section 6, and which one experiment to run next.

* Python standard library only (SQLite included). Developed and tested on Python 3.13; no third-party packages, no network calls.
* **Nothing is scraped.** No login, no API call, no browser automation. Numbers arrive as CSV files you export or type (Ground rule 9: official tools only). `import-queue` reads local files in `pipeline/review-queue/` and never writes to them.
* It does not post, reply or approve anything. Every status is an indication for you to confirm.

## 2. Quick start

From the project folder:

```
python3 analytics/demo_data.py                      # DEMO database + CSVs (all numbers invented)
python3 analytics/dashboard.py --demo               # writes analytics/dashboard_demo.html  (open it in a browser)
python3 analytics/weekly_report.py --demo           # prints a report on the DEMO data

python3 analytics/tracker.py init                   # creates the REAL database (empty) at analytics/data/real/tracker.db
python3 analytics/tracker.py import posts my_posts.csv
python3 analytics/tracker.py import-queue           # optional: register review-queue drafts as posts
python3 analytics/dashboard.py                      # writes analytics/dashboard.html from the real database
python3 analytics/weekly_report.py                  # prints the weekly report from the real database
python3 -m unittest discover -s analytics/tests     # runs the tests
```

`dashboard.html` (real data) shows "NO DATA YET" until you import something. `dashboard_demo.html` always carries a "DEMO DATA" banner.

## 4. The weekly routine (about 30 minutes, the operator's analytics slot in portfolio.md 5.1)

1. **Read the numbers** from each platform's own insights page (or its export) for: every post that is now 7 days old (a second look at day 3 is optional), and each account's day-end follower count and reach.
2. **Type or paste them into the CSV templates** (`templates/post_metrics.csv`, `account_daily.csv`). Blank means "the platform did not show this"; type 0 only for a real zero.
3. **Log the time**: operator minutes per approval, wife minutes per master, N7 recording minutes (`templates/effort.csv`), and every first-pass review verdict (`templates/reviews.csv`). New posts: `posts.csv` (or `import-queue`).
4. `python3 analytics/tracker.py import KIND FILE.csv` for each file. A file with any bad row imports nothing and tells you the line numbers.
5. `python3 analytics/dashboard.py`, open `dashboard.html`; `python3 analytics/weekly_report.py`.
6. Copy the suggested experiment into `experiments.md` (and import it) if you accept it.

## 5. Getting numbers in (CSV)

**What platform exports look like is unverified.** Instagram, Threads and YouTube Studio insights and any export they offer have column names and availability this project has not seen (HUMAN_TODO 10: check what a Taiwan account shows). The importer therefore expects **this studio's own column names**, below. If a platform's export has its own headers, map them instead of editing the file: `--rename "Accounts reached=reach" --rename "Published=published_date"`.

Rules for every import:

* UTF-8, with or without the BOM Excel adds. Dates `YYYY-MM-DD` (`YYYY/MM/DD` is accepted). Whole numbers may have thousands commas (`1,204`). Money may carry `NT$`.
* **Blank = not reported = NULL. 0 = a real zero.** Do not fill saves with 0 on a platform that does not show saves: it would make the saves row look worse than it is.
* Re-importing the same row replaces it (posts by `post_id`, metrics by `post_id` + `snapshot_date`, daily rows by `day` + persona + platform, experiments by `exp_id`). Rows without a natural key (costs, revenue, leads, effort, reviews, standing events) get a hash of their content as `ref`, so importing the same file twice does not double count; give your own `ref` if you want to correct a row later.
* Two genuinely identical rows without a natural key (same date, persona, category and amount, for example) collapse into one because they hash to the same `ref`; give each its own `ref` if that can happen.
* `data/real/.gitignore` keeps the real database out of git by default (delete that file if you want it tracked). **`dashboard.html` is NOT ignored**: once you build it from real data it contains your real numbers, so do not commit it (or add it to `.gitignore`) if the repository is shared. Saved weekly reports (`--out analytics/reports/...`) are ignored.
* A row with more cells than the header is an error (almost always an unquoted `1,200`: put numbers with commas and notes with commas inside double quotes; Excel does this when it saves CSV).
* A file with any bad row imports **nothing** (all-or-nothing); `--skip-bad-rows` imports the good rows instead. Unknown columns are ignored with a warning.
* `DEMO` files and ids are refused by a real database.
* Import order that works: `posts`, then `post_metrics`; `account_daily`, `costs`, `revenue`, `lead_signals`, `effort`, `reviews`, `standing`, `experiments` in any order. `accounts` is only needed for wave 2 and later (pilot accounts are seeded; handles are blank because none is chosen).

`import-queue` registers each `pipeline/review-queue/<persona>/<date>_<NN>/post.json` as a post with status `draft` (the post id is the queue id) and records the wife's **current** `wife_language` state (approved or changes) as a review event with source `queue_snapshot`. The queue holds only the current state, so if she changed a verdict before you ran it, the first-pass verdict is lost: run it after each of her review sessions, or log first-pass verdicts in `reviews.csv`, which is the exact record. It never writes to the queue and never sets any approval field.

## 6. Definitions (portfolio.md 6.1)

* **Week n** of a persona = days 7(n-1) to 7n-1 after its first **published** post (the assumed 2026-11-16 until a real post exists). Weeks 1 and 2 are warm-up; the scoring window is weeks 3 to 6; the week-6 review date is first post + 42 days (2026-12-28 if W0 holds).
* **Organic** = `sponsorship_type` none. Sponsored, gifted and affiliate posts are reported separately and excluded from every median.
* **ER per post** = (saves + shares + comments) / reach, using only the terms the platform reported. If reach is blank the denominator is views and the dashboard says "ER on views". Likes are excluded (stored for reference). Link clicks are excluded and reported weekly per persona (per 1,000 reach).
* **Account figure** = the **median** of post ERs in the window. Minimum sample **8 organic posts per platform**: fewer means extend to week 8, then hold with no scoring.
* **Saves + shares share** = (saves + shares) / (saves + shares + comments), over posts that report saves; unscored where the platform reports none.
* **Review-rejection rate** = first-pass returns or rejections / drafts reviewed, by review date over weeks 4 to 6.
* **Cost** = studio-level tool spend against the NT$5,000 base cap (NT$10,000 headroom). One-time costs (registration, 記帳士, lawyer, TIPO) are outside the cap. **Revenue** counts only rows marked `received`.
* **Cross-platform comparison** exists only for H2 and H3: (shares + comments) per 1,000 views, because views is the one denominator all three platforms are expected to report (unverified).

## 7. The dashboard and the weekly report

**Dashboard** (`dashboard.py`): one scrolling page with a status card per persona (decision path in a collapsible), engagement rate per account (bar = median, dots = posts, threshold lines), saves + shares share, followers and reach per account, weekly link clicks, review rejection and effort against the Keep lines, the capacity check, cost vs revenue against the caps, standing events and experiments, and the threshold table. Every chart has a table view. No external requests; works with scripts off (tooltips and the theme button need the small inline script). Dark and light follow the system, with a theme button (`#dark` or `#light` in the address also forces one). Status is never colour alone (icon plus word). Persona colours follow the persona, not its rank.

**Weekly report** (`weekly_report.py`): deterministic text from the data. Sections: where each account stands; what worked; what did not (the 8 highest-priority lines each, `--all` for the rest); **one** experiment to run next, with its hypothesis, one variable, arms, dates, a decision rule written before the data and a paste-ready CSV row; sample-size caveats. Its rules: a group needs 4 or more posts to be named, a difference is "clear" only at 1.5x or more, it names at most one pattern per account (looking at many groups finds a gap by chance), and it never says a pattern is proven: with 8 to 15 posts per account these are hypotheses. It does not run a significance test. It will not recommend an experiment on a persona that already has one running, or on an account with an open standing gate, and it says plainly when no account has 8 organic posts yet.

## 8. Reading choices and assumptions (where portfolio.md is silent or ambiguous)

Overrule any of these in `thresholds.py` / `decision.py`; the tests will tell you what else moves.

1. **The tree runs per account (persona x platform)**, not per persona, because 6.1 says thresholds are per platform and platforms are not compared. A persona's headline is its best non-paused account. Portfolio.md says "per persona"; this is the smallest change that respects its own per-platform rule.
2. **ER of 2.0% or more that fails any Scale condition falls to the Keep test**, not to Fix.
3. **Scale also requires a rising reach trend** (the 6.1 table lists it in the Scale column; the tree text in 6.3 does not).
4. **Missing effort or rejection data is "unknown"**: it does not block Keep (the status is flagged as provisional on that row) but it does block Scale. Effort needs at least 5 logged units and rejection at least 5 reviewed drafts to be scored (assumption).
5. **"After one redesign"** (6.3 step 3): an effort or rejection value over the retire line counts as a breach only if an experiment of kind `redesign` is marked done; otherwise the account is Fix and the report proposes the redesign. **"After a Fix re-test"**: only an experiment with `is_fix` = 1, status done, whose dates become the re-test window.
6. **Reach trend**: weekly reach (or views); a week-on-week move within 5% is flat (assumption). Rising = no fall in the last two steps and the last week at least 5% above two weeks earlier; falling for 2 or 3 weeks = that many consecutive falls. Fewer than 3 weeks of data = unknown.
7. **The table's other retire-review triggers** (reach falling 3 weeks with ER under 0.6%; target age band under 40%; 10 outreach messages with no lead signal) are shown as WATCH flags. The status follows the tree. Portfolio.md lists them in the table but not as tree steps; decide whether they should escalate.
8. **Followers are advisory** ("record, do not decide on alone"): they never change a status.
9. **Standing gates**: any open event pauses that account (6.3 step 1). A restriction open more than 14 days, or a second Ground-rule-6 event within 8 weeks, shows **Retire**. Repeat disclosure failures in a quarter, two garbled/wrong-fact events in 6 weeks, 5+ "is it real?" comments in a week and 3 near misses in 20 drafts are shown as alerts, not automatic pauses.
10. **Scoring before the week-6 date** gives a provisional reading only when 8 posts are already in the window; otherwise "in progress".
11. **Snapshots**: the latest snapshot per post is used; posts under 7 days old are not excluded (that would break the 8-post minimum at the review date) but are counted as possibly understated.
12. **Link clicks**: the link-page counter is used if it has any data, otherwise platform link taps; they are not added together (double counting).
13. **Capacity check** uses logged minutes only; an incomplete log understates the load. Approvals are counted as published posts.

## 9. DEMO data

`demo_data.py` writes `data/demo/` (a database and `csv/DEMO_*.csv`). All ids start `DEMO-`, the database is flagged `is_demo`, and every page or report built from it says DEMO DATA. The numbers are random draws from invented rates (seeded: the same output every run). They are **not** benchmarks, forecasts or evidence about Taiwan audiences or these personas. The scenario was chosen to exercise the tree (one Keep, three Fix, one Extend, one Pause, a failing hook contrast, a running Fix experiment), so do not read the story as a prediction. The demo date is 2027-01-04. The importer refuses `DEMO` files and ids in a real database, and `demo_data.py` refuses to write inside `data/real/`.

## 12. Limits

* Small samples: a median of 8 to 15 posts is a noisy estimate and small accounts have few interactions per post (the dashboard shows what one interaction is worth). No significance test is run.
* No Taiwan engagement benchmark exists, so the thresholds are unvalidated assumptions.
* Metric availability by platform is unverified; the importer accepts blanks for everything a platform does not show.
* The CSV column names are this studio's own; no platform export has been seen.
* Not tested on Python older than 3.13, on Windows, or with data larger than a few thousand rows.
